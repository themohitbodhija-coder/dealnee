## 1. Outcome, scope, and fixed decisions

Replace Express/MongoDB/Mongoose with hosted Supabase PostgreSQL, Supabase Auth, SQL functions and Supabase Edge Functions. Serve the existing React SPA from Vercel. Store property photos in Amazon S3, delivered through CloudFront from a private bucket. No Express process, EC2 instance, Lightsail instance, or Supabase Storage bucket is needed in the target system.

Start with an empty production database and newly created accounts. Existing production records and photos are disposable dummy content: no Mongo export, password/hash migration, ObjectId conversion job, dual writes, or historical data import. New listing entry and new invitations happen after cutover. Preserve existing UI and workflows except where security or identified correctness defects require a small change, explicitly described below. Do not broaden scope into a framework rewrite, payment system, customer dashboard, or new CRM.

Expected listing turnover is 100–200 new properties/month, with old properties deleted and replaced. This bounds entry volume, not visitor traffic, image bandwidth, or inquiry spam. All GitHub, Supabase, AWS, Vercel, domain, CAPTCHA and email-provider resources belong to the company; named staff receive access, with MFA and company-controlled recovery and billing.

## 3. Target architecture and trust boundaries

1. React → Supabase Auth for signup/password login, recovery, confirmation, session refresh and logout.
2. React → Supabase Data API / narrow SQL RPCs with publishable key and optional user JWT for public catalog reads, own profile, authorized category and inquiry administration. RLS and grants enforce access on every request.
3. React → Edge Functions for public inquiry submission, property save/delete orchestration, image signing/finalization/deletion, view tracking, dashboard aggregation, and Auth administrative operations. Each protected handler verifies an actual user session, checks active profile and live privileges before using elevated clients.
4. React → S3 directly using a short-lived upload signature. Image bytes never travel through Vercel or the old backend. Edge validates uploaded objects before publishing a distinct immutable final object key.
5. Public image requests → CloudFront → private S3 final-image prefix. Pending uploads are never in the distribution's readable origin prefix.
6. Scheduled Supabase job → cleanup Edge Function with dedicated server credential, for pending upload expiry and deletion retries. No always-running worker.

Keep `public` as the exposed schema with tightly granted tables/RPCs. Put authorization records, upload reservations, audit data, rate-limit state and outbox in an unexposed `private` schema. Enable RLS even on internal tables as defense in depth; explicitly revoke public grants. Do not expose `auth.users` or a view of it. RLS filters rows, not columns: private data must be separated or protected by column grants and explicit projection.

Supabase documents RLS and `security_invoker` views; views must not accidentally bypass RLS. Use `security_invoker=true` for any exposed view and test underlying grants, or return an explicit safe projection through a narrowly granted function. Never use `select *` across a public/private join. [Official RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 4. PostgreSQL schema and data contract

Implement timestamped migrations, not dashboard-only edits. Use UUID primary keys (`gen_random_uuid()`); `profiles.id` equals `auth.users.id`. Mongo `_id` becomes UUID `id`; because data is discarded, no legacy-ID column or mapping table is required. Keep human display `property_id` separate from UUID. Existing `/property/:id` routes use UUID after cutover; obsolete dummy ObjectId links show a controlled unavailable page (no fabricated redirects).

All timestamps are `timestamptz`, default `now()`, displayed in the user's locale. Date-only `available_from` and possession dates use PostgreSQL `date` and ISO `YYYY-MM-DD`, avoiding timezone shifts. Optional blank inputs become SQL NULL, not zero, empty dates, `NaN` or the string `"null"`. Explicit false and zero values survive transformations. Prices are INR `numeric(16,2)`; area, dimensions and rates `numeric(14,4)`; no floating-point money. Transfer decimals as strings in the adapter, converting only for formatting with finite/range checks; never rely on JS precision for authoritative comparisons.

### IDs, indexes and functions

Generate display IDs inside the property-create transaction: atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` on counter namespace NP, RS, REN, CB, CL. Format DEL-NP-001, DEL-RS-001, DEL-REN-001, DEL-CB-001, DEL-CL-001; width is minimum 3, expands above 999. All RENT uses one REN counter. Never count live properties or recycle deleted IDs. UI says “assigned on save” before creation; after save show assigned ID. ID immutable on edit even when classification changes. Counters and allocation RPC are never publicly callable.

Indexes: unique display ID; lower(category name); `(status, created_at DESC, id DESC)`; `(property_type, category_id, subtype_code, status, created_at DESC, id DESC)`; partial featured+available index; price, area, bedrooms/bathrooms, furnishing_status and property_age as justified by query plans; FK indexes on property category/author, details/images/units property, inquiry property, user permissions. For literal substring search enable `pg_trgm` with GIN indexes on normalized title/description/city/address and locality (or a generated concatenated search column); verify EXPLAIN with representative data before adding redundant indexes. No blanket GIN on every JSON field. Use same parameterized WHERE for count and page, newest + UUID tie-breaker, page >=1 and limit 1..100.

SQL artifacts: safe public `list_properties`/`search_properties` RPCs (typed optional arguments and explicit DTO), private transactional property save/delete, access helpers, user privilege update, inquiry read-and-mark, dashboard projection, image attach/reorder/remove, view increment, cleanup claim/complete. All SECURITY DEFINER functions use fixed/empty search_path, fully qualified identifiers, no caller-controlled SQL, explicit execute grants and internal authorization; revoke default PUBLIC execute. Prefer SECURITY INVOKER for operations compatible with RLS. Migration tests verify policies cannot recurse through role checks.

Proposed correction follows existing UI capabilities rather than broken `manage_admin` routing. Admin bypass is server-side. Delegated permissions only work with role=subadmin and active=true. `view_inquiries` retains existing page's read/status/delete operations despite its label; document this in grant UI. Accounts are active unless deliberately disabled/deleted. No frontend session object, signup metadata, or JWT `user_metadata` is trusted as authorization.

`private.has_permission()` / `private.is_admin()` derive auth.uid() and read live `user_access`, not JWT role claims. Narrow definer helper owns only what it needs and does not expose role tables through Data API. Anonymous access uses explicit read policies. Property/details/units/images public SELECT only exposes committed listing content. No draft rows are in public tables; staged upload reservations stay private. Signed-in inactive/deleted actors lose administrative/profile access immediately even with an otherwise unexpired JWT. Public read remains public.

RLS/grants: profiles self SELECT/UPDATE (column-grant only name/phone/profile image; ID/timestamps cannot be changed); wishlist self CRUD; categories public SELECT and permission-gated mutations; taxonomy public SELECT only; property tables public SELECT with no browser INSERT/UPDATE/DELETE grants (all mutations through gated transactional save); inquiries permission-gated SELECT/status UPDATE/DELETE, no anon or ordinary-user read/write. Direct inquiry UPDATE is restricted to status only; read-and-mark RPC atomically sets read. Internal tables deny browser access. Elevated Edge clients bypass RLS, so each service-role operation must have explicit authorization and narrow validated inputs. Use user-scoped clients where possible.

Dashboard aggregates must not leak counts or recent inquiry PII to subadmins lacking the relevant permission. Show hidden/unavailable sections instead of fabricated zeroes. This is a necessary UI adjustment.

## 6. Authentication and administrative account lifecycle

- Add one Supabase JS v2 client. SPA session persistence is managed by the SDK (choose sessionStorage to preserve current “browser close clears session” preference); enable SDK auto refresh and URL session detection, one storage key per environment. Tokens are browser-accessible in a SPA: apply CSP, avoid unsafe HTML, review third-party scripts. No homemade HttpOnly-cookie system is retained.
- Register with email/password and sanitized name/phone metadata, email confirmation enabled. Show “check your email” if no session yet, instead of treating signup as automatic login. Untrusted metadata may initialize only safe profile fields.
- `auth.users` insert trigger creates profile and default regular-user access atomically; safe defaults for absent metadata, no copied role/permissions. Trigger failure can block signup, so test it explicitly. [Supabase user-data pattern](https://supabase.com/docs/guides/auth/managing-user-data).
- Login through `signInWithPassword`; load safe profile + own effective capabilities. AuthProvider initializes through SDK, subscribes to auth state, handles refresh, expiry, multi-tab changes, loading and errors; do async profile loading outside auth callback lock-sensitive paths. Never render protected pages before initialization completes. Route guards do not grant access.
- Logout with SDK signOut (explicit normal logout scope), clear in-memory query/profile state, old sessionStorage `user`, legacy token state and account-specific wizard drafts. After timeout or revocation show login; do not redirect anonymous catalog errors into a refresh loop. An issued JWT may outlive logout, so all privileged operations also require live active access; document Supabase session revocation semantics and test deleted-account handling.
- Add forgot-password, auth callback, and update-password routes. `resetPasswordForEmail` sends generic success regardless of existence; callback handles PKCE code exchange where required, PASSWORD_RECOVERY, expired/reused links, confirmation and invite acceptance, then `updateUser({password})`. Password entry via invite/recovery belongs to the invited person, not a staff member choosing their password.
- Configure production Site URL to canonical company domain; allow exact confirmation/recovery callback URLs and localhost:3001 in local/staging only. Preview deployments use separate staging Supabase and stable staging callback hostname; never wildcard all Vercel previews into production redirects. Validate return paths against local allowlist to prevent open redirects. [Redirect URL documentation](https://supabase.com/docs/guides/auth/redirect-urls).
- Configure company-domain custom SMTP, SPF/DKIM/DMARC, templates and sender; verify signup, reset and invite delivery to non-team addresses, spam/bounce handling, resend cooldowns, email rate limits and CAPTCHA. Default Supabase SMTP is not a production delivery service and restricts recipients. Use provider API over HTTPS for any Edge-sent notifications; no inquiry email side effect exists today, so do not invent one. [SMTP restrictions](https://supabase.com/docs/guides/auth/auth-smtp).
- Bootstrap first admin through a one-time company-controlled operator script: create/invite Auth account, verify intended UUID, then apply privileged access via restricted DB operation. No public bootstrap endpoint, default password or committed credentials. Store safe UUID/actor audit evidence. Remove/revoke bootstrap credential when done; confirm a second company recovery owner.
- `admin-users` Edge handles paginated user list, invite, delete and explicit privileged access changes. Derive actor from verified user JWT and live access, never request body. Retrieve Auth emails only on authorized server projection. Subadmin manager can only act on regular users, cannot set grants/role, cannot target staff or itself. Admin grants validate exact enum/list, active account, reauthentication for high privilege; serialize last-admin changes with lock to prevent concurrent removal. Pending invited staff have no usable session; activate intended privilege only through audited verified flow.
- Coordinate Auth API with database operations: use idempotent invite records, inactive/pending account state and reconciliation for failure between Auth creation and access assignment. For deletion first deactivate/revoke privileges, detach `posted_by` (SET NULL), cancel uploads and record audit, then delete Auth user; retry safely if Auth fails. Preserve public properties and inquiry snapshots. Auth API calls and Postgres cannot form one transaction; never report success for a partial failure.

## 8. S3 upload, image delivery and deletion design

Use separate staging and production buckets and CloudFront distributions, or equivalently strict isolated bucket resources. Company selects region near users/Supabase database after latency/cost review. Enable Block Public Access, bucket-owner-enforced Object Ownership (ACLs disabled), HTTPS-only bucket policy and default SSE-S3 encryption. CloudFront OAC reads only final `properties/*` prefix of the S3 REST origin, not website hosting or pending prefix; bucket policy binds distribution SourceArn. No public bucket policy. [CloudFront OAC and object ownership](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

1. Wizard asks `image-upload-init` with target property UUID for edit (or a server-issued create-session UUID), file count, MIME, size and optional SHA-256. Handler verifies manage_properties/admin, ownership of upload session and remaining quota, validates supported raster MIME/extension and <=5 MiB, reserves total slots (max20 across existing+new, not20 per request), generates random pending object key and returns a 5-minute signed upload URL/form and opaque reservation ID. Client cannot choose bucket/key/ACL or overwrite an existing image.
2. Prefer S3 presigned POST policy (signed URL plus required form fields) with exact key, MIME, expiry and `content-length-range` 1..5242880; browser sends directly to S3. If PUT is selected during runtime proof, signed headers/checksum and post-upload actual size enforcement are mandatory; MIME declaration alone does not prove content and browser headers do not provide a reliable policy size cap. Document selected contract in `s3-images.md`. Presigned credentials are bearer capabilities, reusable until expiry; do not log them. [Presigned URL semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [S3 POST policies](https://docs.aws.amazon.com/AmazonS3/latest/API/sigv4-HTTPPOSTConstructPolicy.html).
3. `image-upload-finalize` verifies reservation still valid, actor and property/session match, object exists, size/checksum/MIME metadata match; fetches bounded bytes to verify PNG/JPEG/GIF/WebP/AVIF magic and actual decodability, bounded dimensions/pixel count. Reject SVG/HTML/executables, truncated/polyglot inputs where detectable, image bombs and unsupported encodings. Preserve source formats initially; strip sensitive EXIF GPS metadata using a proven Deno-compatible decoder if feasible. Benchmark validation per format against Edge CPU/memory before committing; if full decoding exceeds runtime limits, use a narrowly scoped managed image-processing job, never silently drop validation or restore Express. This is a phase-2 technical spike gate, not permission to claim completed support.
4. Publish a new random immutable final key from validated bytes, not an overwritable pending key. Signing URL reuse must never change a published image. Pending key is not publicly readable. Store final metadata with reservation, then `property-save` attaches only validated, same-actor/same-target IDs in one DB transaction. Unique attach enforces single use. Attaching existing images requires that they already belong to target property; fabricated/cross-property keys are forbidden.
5. Wizard sends ordered retained image IDs and new validated IDs. Removing/reordering cover updates DB order transactionally; require >=1 image on completed new listing (current final form rule), max20 overall. Existing image removal while editing must not delete until save succeeds. Failed save leaves old listing/photos intact; unattached validated uploads expire for cleanup. Client timeout retries same idempotency key; explicit cancellation and upload errors are recoverable.
6. Return stable HTTPS CloudFront URLs derived from server-known final keys. Use immutable caching for unique keys, correct Content-Type and `nosniff`. Lightbox downloads use fetch, so configure CDN GET/HEAD response CORS for actual frontend origins and expose necessary headers; make download filename behavior explicit. Allow S3 POST (or PUT), HEAD as needed and exact production/staging/local origins; allow only used headers. Do not enable arbitrary-origin credentialed CORS. Direct image reads via CDN are intentionally public; private bucket does not make public listing images confidential.
7. Property/image deletion transaction records final keys in outbox before metadata removal. Worker claims bounded jobs, DeleteObject (and any necessary versions), retries with backoff and dead-letter alarm; no DB/S3 pretend transaction. CDN invalidation required for prompt removal of cached photos; otherwise document bounded TTL. “Deleted from website” is distinct from backup retention.
8. Scheduled cleanup expires abandoned reservations (initial 24 h), invalid images and unattached final objects after grace period, checks DB attachments under lock before deletion, and processes deletion outbox. S3 lifecycle expires pending prefix (e.g. 2 days) and aborts incomplete multipart uploads as secondary safety. Periodic inventory reconciliation flags final orphans; never TTL-delete referenced final keys. Cleanup failures alert company operator.

IAM: dedicated non-root application principal with only PutObject/GetObject/DeleteObject on environment-specific pending/final prefixes and ListBucket restricted by prefix where reconciliation requires it; no wildcard account access, ACL changes, bucket policy changes or bucket deletion. Separate deployment/control-plane IAM from runtime signer. CloudFront origin has its own read-only bucket access. Supabase Edge has no EC2 instance role: use scoped server-held AWS access keys initially, rotate and audit them; if using STS credentials, supply session token and refresh before expiry via a proven mechanism. Do not assume automatic IAM role discovery. AWS credentials, signed URLs and secret Supabase key never go in React, GitHub logs, inquiry responses or localStorage.

## 9. Public input validation and abuse controls

`submit-inquiry` accepts only name/email/phone/message/property/idempotencyKey/CAPTCHA token, bounded JSON body (e.g.16 KiB); trims strings, validates practical email and normalized phone, UUID property association, no arbitrary status/actor/privileges. Treat message as plain text on output, no unsafe HTML. CAPTCHA verification uses server secret and hostname/action checks; honeypot and minimum-fill-time are supplemental. Apply atomic database-backed rate limits by privacy-preserving hashed trusted client-IP signal and email, plus global circuit breaker (initial 5/minute/IP, 20/day/email, tune after real traffic). Do not trust caller X-Forwarded-For blindly; verify platform header provenance. Invalid CAPTCHA/oversized input is rejected before insertion; no direct Data API INSERT path bypasses controls. Return generic safe messages and429 retry guidance, avoid email/account enumeration.

Auth signup/reset use Supabase CAPTCHA/rate limits and production SMTP limits. View tracking is separately rate limited/deduplicated and increments only an existing public listing, no general public UPDATE. Counts represent approximate visits, not unique analytics. Image signing has actor/day/file-count/byte quotas, not only CORS. Keep PII out of logs; record request IDs, status, latency and safe resource IDs, with short retention for anti-abuse hashes.
